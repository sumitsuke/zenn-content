案件の転記を自動化して、台帳を JSONL（1 行 1 案件）で持っています。書くのは自作の取り込みスクリプト、読むのは点検スクリプト（`reconcile.py` ほか）で、どれも自分の道具です。

この記事は、その台帳で**実際に踏んだ 1 件**（U+2028 で JSONL の 1 行が 2 行に割れた）と、それをきっかけに**台帳 973 件を数えて見えた 3 つの論点**（入力のゆれ＝全角数字・空の表現と型・日付の書式／すでに運用ルールがある重複／まだ測っていない冪等）を、数えた数字と一緒に書いたものです。

発注側の「自動化を頼む前に決めておくこと」ではなく、実装側で自分が踏んだものと、数えた数だけを書きます。

## 前提: 台帳の形

- 台帳は `ledger.jsonl`（案件台帳・名前は一般化）。1 行が 1 案件の JSON で、日本語を読める形で保ちたいので `json.dumps(rec, ensure_ascii=False)` で書く
- **取り込み経路は追記のみ**。既存行には触れない（`append_jsonl`）。ただし台帳ツールには更新系（`--update` / `--refresh`）があり、こちらは `.bak` を取ってから**全行を書き直す**（`rewrite_jsonl` → 一時ファイル → `os.replace`）。「追記のみ」は取り込みの話です
- 読む側は複数ある。`reconcile.py`（`--quick` で E「案件台帳の健全性」などを点検）、送信前点検、`make_next_list` など
- 2026-09-16 時点で record は **973 件**

## 1. U+2028 で 1 行が 2 行に割れた（2026-09-12）

### 何が起きたか

台帳のある 1 件の `body`（本文）に U+2028（LINE SEPARATOR、行区切り文字）が混じっていました。エディタで開いても気づきにくい文字です。

- ファイル上の改行コード（`\n`）は 1 行に 1 つで、`json.loads` 自体は通っていた
- ところが `splitlines()` で 1 行ずつ読む器（`reconcile` の E・送信前点検・`make_next_list` など）が、その行を **2 行に割って** 読み、「解析不能」の赤を出した

Python の `str.splitlines()` は `\n` だけでなく U+2028 も行境界として扱う（[公式ドキュメント「str.splitlines()」の行境界の表](https://docs.python.org/ja/3.12/library/stdtypes.html#str.splitlines)）ので、JSON としては正しい 1 行が、読む側では 2 つの壊れた断片になります。

![対処前は生の U+2028 が本文に残り、splitlines() で 2 行に割れて「解析不能」になる。対処後は \u2028 の 6 文字に置換され、1 行のまま json.loads で元の文字に戻る](/images/jsonl-u2028-ledger-drift/fig1_u2028.png)
*図 1: 書く側で 1 か所だけ直す。読む側（複数）は触らない。*

### 手元で再現（Python 3.12.10）

台帳と同じ書き方で 1 行作り、`splitlines()` に通すとこうなります。

```python
import json

rec = {"id": 1, "body": "前半\u2028後半"}
line = json.dumps(rec, ensure_ascii=False) + "\n"

len(line.split("\n")) - 1     # 1  … 改行コードは 1 つ
len(line.splitlines())        # 2  … ここで割れる
json.loads(line) == rec       # True … JSON としては正しい

json.loads(line.splitlines()[0])
# JSONDecodeError: Unterminated string starting at: line 1 column 19 (char 18)
```

「`json.loads` は通るのに点検だけ赤」の正体はこれでした。

整理すると、壊れたのは JSONL ではなく**読む側**です。JSON Lines のレコード区切りは LF（`\n`）で、`splitlines()` はそれ以外（U+2028 など）まで境界にします。正攻法は読む側を `split("\n")` に揃えることで、下の「書く側で塞ぐ」は、読む側が複数あって今すぐ全部は触れない状況での**互換策**です（仕様の境界と、既存系への封じ込めは別の話として分けておきます）。

### 対処: 書く側の `dumps_line()` で U+2028 / U+2029 を JSON エスケープにする

読む側は複数あるので、読む側を全部直すのではなく、**書く側の 1 か所**で潰しました。最初に入れた修正がこれです（この時点では 2 文字だけ。後の検証で足りないと分かります＝次の節）。

```python
def dumps_line(rec):
    """1 行 1 案件を守る json.dumps。U+2028/U+2029（行区切り文字）を JSON エスケープにする。
    2026-09-12: ある行の body に U+2028 が入り、splitlines() で読む器（reconcile E・送信前点検・
    make_next_list 等）が 2 行に割って「解析不能」と赤を出した（json.loads 自体は通っていた）。
    ensure_ascii=False は残す（日本語を読める形で保つ）。値は同一（デコードすると元の文字に戻る）。"""
    return json.dumps(rec, ensure_ascii=False).replace("\u2028", "\\u2028").replace("\u2029", "\\u2029")


def append_jsonl(rec):
    # 追記のみ。既存行には一切触れない。
    with open(JSONL, "a", encoding="utf-8") as f:
        f.write(dumps_line(rec) + "\n")
```

ポイントは 3 つ。

U+2029（PARAGRAPH SEPARATOR）は今回の事故では出ていませんが、同じ理由で一緒にエスケープしています。手元で確かめると、生の U+2029 を含む 1 行も `splitlines()` は 2 行に割り（`json.loads` は通る）、エスケープすれば 1 行に戻って値も一致しました＝**予防的な対処**です。

1. **`ensure_ascii=False` は残す。** `ensure_ascii=True` にすれば U+2028 も `\u2028` になって同じ問題は消えますが、日本語が全部 `\uXXXX` になって台帳を目で読めなくなる。読めることが台帳の価値なので、行区切り文字 2 つだけを狙って置換しています
2. **値は変わらない。** `"\u2028"` は JSON の正規のエスケープなので、`json.loads` すると元の U+2028 に戻ります。台帳の中身を書き換えたのではなく、表現だけを変えています
3. **docstring に日付と事故の経緯を書いておく。** 「なぜこの `replace` があるのか」は半年後の自分が必ず消したくなるので、消せない理由をコードの隣に置いています

同じ `replace` を上の再現コードに足すと、`splitlines()` は 1 行を返し、`json.loads` の結果は元の `rec` と等しいままです。

**すでに保存済みだった行はどうなるか。** `dumps_line()` は書く側なので、直した時点では過去の行に生の U+2028 が残ります。ここは更新系が拾いました——`--update` / `--refresh` は全行を `dumps_line()` で書き直すので、次に更新が走った時点で既存行もエスケープに変わります。実測（2026-09-16）では台帳 973 行に**生の U+2028 は 0 個**、エスケープ表記が 1 か所。狙って直したのではなく、全書き直しの経路が結果的に拾った形です。

## 1b. 塞ぎ切れていなかった: U+0085

`str.splitlines()` が行境界として扱う文字のうち、`json.dumps(ensure_ascii=False)` の出力に**生のまま残る**のは 3 つでした（2026-09-16 に実測）。

| 文字 | dumps の出力に生で残るか | `splitlines()` が割るか |
|---|---|---|
| U+2028 LINE SEPARATOR | 残る | 割る |
| U+2029 PARAGRAPH SEPARATOR | 残る | 割る |
| **U+0085 NEXT LINE** | **残る** | **割る** |
| U+000B・U+000C・U+001C〜U+001E | 残らない（`\u000b` などにエスケープされる） | 割らない |

つまり `dumps_line()` は 3 つのうち 2 つしか塞いでいませんでした。U+0085 を含む 1 行を通すと `splitlines()` は 2 行を返します。台帳には現状 0 個ですが、同じ事故が起きる経路が空いたままだった、ということです。

**その場で 3 つ目を足しました。**

```python
def dumps_line(rec):
    _s = json.dumps(rec, ensure_ascii=False)
    for _ch, _esc in (("\u2028", "\\u2028"),
                      ("\u2029", "\\u2029"),
                      ("\u0085", "\\u0085")):
        _s = _s.replace(_ch, _esc)
    return _s
```

docstring も「U+2028/U+2029」から 3 文字に直しました（コードだけ直して説明文が古いまま、を避けるため）。毒を 3 種類（U+2028 / U+2029 / U+0085 と、3 つ同時）入れて確かめた結果がこれです。

| 入れた毒 | `splitlines()` | `json.loads` で元の値に戻るか |
|---|---|---|
| U+2028 | 1 行 | 戻る |
| U+2029 | 1 行 | 戻る |
| U+0085 | 1 行 | 戻る |
| 3 つ同時 | 1 行 | 戻る |

日本語がエスケープされていないこと（`ensure_ascii=False` が効いたまま）も同じテストで見ています。穴は「行区切り文字 2 つ」ではなく **3 つ**で、2 つ塞いだ時点では「塞いだつもり」でした。**同じ関数を書くなら、`splitlines()` の境界のうち出力に生で残るものを 1 回数えてから**です。

## 2. 全角数字: 52 件が台帳に残っている

U+2028 を見つけたついでに、台帳を Python で数えました。全角数字（０〜９）を含む record は **52 件**。欄別では次の通りです。

| 欄 | 全角数字を含む record |
|---|---|
| `body` | 50 |
| `title` | 8 |
| `notes` | 3 |
| `judgment_reason` | 1 |

（1 record が複数の欄で数えられるので合計は 52 を超えます）

この記事の件数は、台帳の JSONL を次のように数えたものです（同じ形で誰でも数え直せます）。

```python
import json, re, collections, io
rows = [json.loads(l) for l in io.open('ledger.jsonl', encoding='utf-8') if l.strip()]
len(rows)                                                     # 973
sum(1 for r in rows if re.search(r'[０-９]', json.dumps(r, ensure_ascii=False)))   # 52
collections.Counter(type(r.get('applicants')).__name__ for r in rows)             # int 910 / str 63
collections.Counter(re.sub(r'\d', 'n', str(r.get('deadline'))) for r in rows)     # 書式ごとの件数
```

台帳ツール（`ledger.py`・名前は一般化） には `unicodedata` の import が無く、`normalize` / `translate` / `maketrans` のいずれも 0 件（2026-09-16 に grep）。実際に全角のまま 52 件が残っていることと合わせて、**取り込みの経路では揃えていない**と読めます（呼び出し経路を全部追ったわけではないので、言えるのはこの範囲まで）。

ほとんどが `body`（本文）で、本文は人が読む欄なので、今すぐ壊れるものではありません。ただ、Python の `int()` は全角の `３` も受け取り（[int() の仕様](https://docs.python.org/ja/3.12/library/functions.html#int)）、正規表現の `\d` も**既定の Unicode パターンなら**全角数字に一致します（`re.ASCII` を付けると一致しません＝実測）。一方で文字列としては `"3" == "３"` は `False` です。ASCII 数字の文字列一致に頼る検索・突き合わせでは、全角で書かれた側が一致しません（どの 52 件がどの検索に当たるかまでは数えていません）。**正規化するなら書く側で、しないなら「読む側で全角を前提にする」と決めておく**必要があります。この台帳は現状「何も決めていない」状態で、それが 52 件という数で見えた、というのがここの結論です。

## 3. 欠損値と数値型が混ざっている: `""` と `0` は別のもの

同じ計測で、いちばん効きそうだったのがこれです。

**`""` と `0` が同じ欄に両方ある欄**（どちらも「空」に見えるが、意味は別）:

`reply`, `contracts`, `client_orders`, `client_order_rate`, `applicants`, `drop_rank` の 6 欄

**同じ欄に型が混在している**:

| 欄 | `int` | `str` |
|---|---|---|
| `applicants` | 910 | 63 |
| `budget_min` | 506 | 467 |

**日付欄の書式ゆれ**:

| 欄 | `nnnn-nn-nn` | `""`（空文字） | `あとn日（n月n日まで）` | `本日終了（n月n日まで）` | 計 |
|---|---|---|---|---|---|
| `posted_date` | 723 | 250 | — | — | 973 |
| `deadline` | 811 | 153 | 7（1 桁 5 件 + 2 桁 2 件） | 2 | 973 |

![applicants は int 910 / str 63、budget_min は int 506 / str 467。posted_date は日付 723 / 空文字 250、deadline は日付 811 / 空文字 153 / 「あとn日」7 / 「本日終了」2](/images/jsonl-u2028-ledger-drift/fig2_types.png)

### なぜ効くか

`str` 側の中身を数えると、`applicants` の 63 件も `budget_min` の 467 件も**すべて空文字 `""`**（数字を文字列で持っている行は 0 件）でした。つまり型の混在の正体は「**値が無いときだけ `""` になる**」ことです。

そして同じ欄に `0`（`int`）も 31 件あります。**`""` は「取れなかった」、`0` は「0 人だった」で、意味が違います。**

これは値の見た目からの推測ではなく、取り込み器の実装がそうなっています——応募者数を拾う関数は、どのパターンにも一致しなかったときに `""` を返し（`return ""`）、ページに数字が書かれていればそれを `int` にします。つまり `0` は「0 と書かれていた」、`""` は「書かれていなかった／取れなかった」です。

これが効くのは、数値として扱う場面です。「応募 0 件の案件」を `== 0` で数えると `""` は一致しない一方、`not applicants` で数えると「未取得（`""`）」と「0 人（`0`）」が同じ側に入ります。`budget_min` は 467 / 973 が `""` なので、`sorted()` や `max()` に素直に渡せばその時点で `TypeError` です。

直し方は「空をどれか 1 つに統一する」ではありません。**`0` は空ではなく実測値**なので、統一すると「0 人だった案件」が消えます。決めるのは型のほうです——**数値欄は `int | None`**（取れたら `int`（0 を含む）／取れなければ `None`）。こうすると読む側は `is None` で欠損だけを外せて、`0` は数えたい場面で数えられます。

`deadline` の「あとn日（n月n日まで）」7 件と「本日終了（n月n日まで）」2 件は、括弧内に月日はあるものの年が無く、`nnnn-nn-nn` の 811 件と同じ扱いでは比較も並べ替えもできません。件数は少ないですが、**書式が 1 つでも混ざると読む側に分岐が生える**種類のゆれです（この 9 件は一覧ページの表示文字列がそのまま入ったもので、日付に直す処理を通っていません）。

これも全角と同じで、書く側で揃えていないから起きています。空は `null` か `""` か `0` か、数値欄は `int` に寄せるのか、取り込み時に 1 回決めておけば、読む側（点検・一覧・集計）が全部楽になります。

## 4. 重複: 消さずに `outcome` に印を付け、数える側で引く

台帳に行を消す操作はありません（更新系は全行を書き直しますが、行を削る操作は無い）。重複だと分かった行も消さず、代わりにその行の `outcome` に **`重複(IDnに統合)`** と統合先の ID を書きます（台帳ツールの `--update N outcome=重複(IDnnに統合)`）。

`reconcile --quick` の E は、それを前提にこう数えています（2026-09-16）。

| `record_count` | 973 |

Python で数え直した側も、`outcome` が `重複` / `重複(IDnに統合)` の行は **31 件**、`id` の重複は **0 件**で、E の数字と一致しました。

重複と分かった行の**取り込み日**（`captured_date`＝取り込み時に付ける日付。重複と判定した日ではありません）の上位 5 日は `2026-08-06` に 8 件、`2026-07-15` に 5 件、`2026-08-25` に 5 件、`2026-08-24` に 4 件、`2026-08-26` に 3 件。特定の日にまとまって出ているので、「取り込みの重なった日」を後から追えるのも、行を消さない利点です。

ちなみに E の `status` は 2026-09-16 時点でまだ「ズレ」（summary: `URL欠落または重複を検出`）です。`duplicate_url_group_count` が 0 なので、残っている赤は `missing_url_count` 46 件の側だと読めます。片付いたのは**既知の重複 31 件と、URL が一致する重複**までで、「URL も ID も違うが中身は同じ」型の重複を数えたわけではありません。そこは未確認です。

## 扱わなかったこと: 冪等の実測

「同じ取り込みを 2 回走らせても件数が増えないか」も確かめたい項目でした。設計としては、取り込み器が `id` で既存判定をして追記だけを行う（`append_jsonl` は既存行に触れない）ので増えないはずです。

ただ、**「2 回走らせて件数が同じだった」という実走ログはまだ取っていません**。設計の説明だけで「冪等です」と書くのは違うので、この記事では数字を出しません。取ってから別に書きます。

## まとめ: 書く側で 1 回決めておくこと

台帳 973 件を数えて出てきたものは、状態が 4 つに分かれます。決まっているもの・決めていないもの・まだ測っていないものを混ぜないのが大事なところです。

| 項目 | 状態 |
|---|---|
| U+2028 / U+2029 / U+0085 | **実事故 1 件（U+2028）・3 つとも対処済み**（U+2029 と U+0085 は予防・§1b で毒 4 ケースを確認） |
| 全角数字・欠損と型・日付の書式 | **実測で確認したゆれ・方針は未確定**（書く側で何も決めていない） |
| 重複 | **既存ルールで処理済み**（消さずに `outcome` へ統合先 ID・31 件・`id` 重複 0） |
| 冪等 | **設計上の想定のみ・実走ログ未取得** |

2 行目については、取り込みの経路に正規化が無く（`unicodedata` の import 無し）、元の表記がそのまま入っています。ただし、ゆれが「仕様を決めていなかったから」なのか、取得元の表現差なのか、過去の仕様変更の名残なのかまでは、件数だけでは分けられません。ここで言えるのは「今そうなっている」ところまでです。

- [x] **行区切り文字**: U+2028 / U+2029 / **U+0085** の 3 つを書く側でエスケープする（`ensure_ascii=False` は残す）。→ §1b で 3 つ目を足し、毒 4 ケースで確認済み
- [ ] **全角数字**: 正規化するなら書く側で。しないなら読む側で全角前提と決める（現状 52 件が未処理）
- [ ] **欠損と 0 を分ける**: 数値欄は `int | None`（取れたら `int`（`0` を含む）／取れなければ `None`）。`""` と `0` を同じ「空」にまとめない（現状 6 欄で混在・`applicants` は `""` 63 件と `0` 31 件が同居）
- [ ] **重複**: 行は消さず `outcome` に統合先 ID を書き、数える側で引く（31 件、`id` 重複 0）
- [ ] **冪等**: 設計だけでなく、2 回走らせたログを取る（未了）

書く側は 1 か所、読む側は複数。直すなら書く側です。

この記事の本家（検証環境・判定・証拠）は Sumitsuke Lab → [JSONL の「1 行」を割る不可視文字は 3 つだった（検証の記録つき）](https://sumitsuke.jp/via/zenn/lab/jsonl-line-separators-three/)。

### AI の利用について

この記事は実験の検体です。題材の絞り込み・構成・本文・図・公開前セルフチェックまでを AI（Claude Opus・素の環境＝プロジェクト設定も記憶も無し）が行い、人は材料を渡して 1 文の指示を出しただけです。公開前に、いつもの検証工程（数字・引用・再現コードを一次資料と突き合わせ、公開の規則に照らす）を通してからこの版を出しています。台帳は自分の道具で、顧客名・相談内容・案件の識別子は含みません。
