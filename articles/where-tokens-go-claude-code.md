Claude Code を 1 日使うと、トークンがどこかへ大量に消えます。私は「基礎のコンテキスト（CLAUDE.md・記憶・道具一覧など）が 9 万トークンもあるから」と思い、まず基礎を削りました。試算したら **−2.7%**。usage を応答単位に分解し直したら、効いていたのは**往復（API 応答）の数**でした。往復を 23% 減らす試算は **−20%**。

一番の教訓は「削る前に、課金と usage の単位を間違えていないか確かめる」でした。私は転写を**行**で数えて誤診しています。

**先に断っておくこと**: この記事の 35／20／45% や −2.7／−20／−32% は、**生のトークン数の比率ではなく、比較用の重みを掛けた usage スコアの内訳**です。重みは「キャッシュ読み 0.1／キャッシュ書き 2／出力 5／入力 1」で、料金表でも公式仕様でもありません。生のトークン数は別に表で出します。

## 先に結論

- 1 依頼（定型の事務作業・62 応答）の重み付きスコアの内訳＝**基礎相当量の再計上 35%／自分の出力 20%／積み上がった会話の再計上ほか 45%**。「基礎相当量」＝1 応答目に載っていた cache_creation＋cache_read（89,507）で、指示書・道具一覧・設定・記憶などの proxy。各部位の内訳は測っていない。
- 基礎を 8K トークン削る試算＝**−2.7%**。応答数を 23% 減らす試算＝**−20%**（38% なら −32%）。**この転写とこの比較モデルでは**、基礎 8K の削減より不要な往復の削減の寄与が大きかった——言えるのはここまで（Claude Code 一般の比率ではない）。
- 理由は、基礎も積み上がった会話も**応答のたびに usage 上で再計上される**から。削る量より「毎回払う回数」が効く。
- 最初は転写を**行**で数えて 42／39／18% と出し、「出力が重い」と誤診した。1 応答は複数行に分かれて記録され、各行が同じ usage を持つ。`message.id` で 1 応答 1 回に直すと 35／20／45%。

## 転写はどこにあり、何が書いてあるか

```
~/.claude/projects/<プロジェクト名>/<セッションID>.jsonl
```

`type == "assistant"` の行の `message.usage` に、その応答の `input_tokens`／`cache_creation_input_tokens`／`cache_read_input_tokens`／`output_tokens` が入っています。

罠が 1 つ。**1 つの API 応答が複数行に分かれて記録されます**（思考・本文・tool_use がそれぞれ 1 行）。各行が同じ `usage` を持つ。今回の依頼①は 62 応答で 106 行＝行で足すと **1.7 倍**に膨らみます。1 応答を 1 回だけ数える鍵は `message.id` です。

## 集計スクリプト（外部依存なし）

```python
import json, sys, collections

W = dict(input=1.0, cache_creation=2.0, cache_read=0.1, output=5.0)  # 比較用の重み。料金表ではない

seen = collections.OrderedDict()
for line in open(sys.argv[1], encoding="utf-8"):
    d = json.loads(line)
    if d.get("type") != "assistant":
        continue
    m = d["message"]; u = m.get("usage") or {}
    if not u or m["id"] in seen:          # 同じ応答の 2 行目以降は数えない
        continue
    seen[m["id"]] = dict(input=u.get("input_tokens", 0),
                         cache_creation=u.get("cache_creation_input_tokens", 0),
                         cache_read=u.get("cache_read_input_tokens", 0),
                         output=u.get("output_tokens", 0))

resp = list(seen.values()); N = len(resp)
c0, r0 = resp[0]["cache_creation"], resp[0]["cache_read"]
base = c0 + r0                                   # 1 応答目に載っていたもの＝基礎
tot = {k: sum(r[k] for r in resp) for k in W}
raw = sum(tot.values())
eff = sum(tot[k] * W[k] for k in W)
base_eff = c0*W["cache_creation"] + r0*W["cache_read"] + base*W["cache_read"]*(N-1)  # 1 応答目は書き、以後は読み
out_eff = tot["output"] * W["output"]
rest = eff - base_eff - out_eff
print(f"応答 {N} 回／基礎 {base:,} トークン")
print("生トークン: " + " ".join(f"{k} {100*tot[k]/raw:.0f}%" for k in W))
print(f"重み付きスコア {eff/1e6:.2f}M: 基礎の再計上 {100*base_eff/eff:.0f}%／出力 {100*out_eff/eff:.0f}%／積み上げの再計上ほか {100*rest/eff:.0f}%")
print(f"基礎を 8K 削ると {100*8000*W['cache_read']*(N-1)/eff:.1f}% 減")
cc_acc = tot["cache_creation"] - c0; cr_acc = tot["cache_read"] - r0 - base*(N-1)
for cut in (0.23, 0.38):
    e2 = (tot["input"] + c0*2 + r0*0.1 + cc_acc*2*(1-cut)
          + (base*(N-1) + cr_acc)*0.1*(1-cut) + tot["output"]*5*(1-cut*0.5))   # 出力は半分だけ減ると仮定
    print(f"応答を {int(cut*100)}% 減らすと {100*(1-e2/eff):.0f}% 減")
```

1 応答目は基礎を「書き」（cache_creation）、2 応答目以降は「読み」（cache_read）として数えます。最初の版はこの 1 応答目を書きと読みの両方で数えていましたが、直しても内訳は 44→45% が動いただけで、試算の値は変わりませんでした。

⚠ 区間の端は **21:40:00〜22:16:00（UTC）** で切っています。終わりの 1 分を丸ごと含める（22:16:59 まで）と 2 応答増えて **64 応答・110 行**になり、内訳は 34／20／46% に動きます。試算（基礎 −8K で −2.7%、応答 −23% で −20%、−38% で −32%）はどちらの切り方でも同じでした。

## 依頼①の結果

まず生のトークン数（重みなし）。

| 種別 | トークン | 比率 |
|---|---|---|
| cache_read | 10,335,693 | **97%** |
| cache_creation | 201,267 | 2% |
| output | 73,735 | 1% |
| input | 124 | 0% |

数だけ見れば 97% がキャッシュ読みです。これに重みを掛けたスコア（合計 約 1.80M）の内訳がこちら。

| 項目 | 値 |
|---|---|
| 応答数（`message.id` の一意数） | 62（うち本文だけの応答 1） |
| 基礎相当量（1 応答目の cache_creation＋cache_read・基礎の proxy） | 89,507 トークン |
| 基礎の再計上 | **35%** |
| 自分の出力 | **20%** |
| 積み上がった会話の再計上ほか | **45%** |

依頼①は「公開ページを読んで台帳に記帳する」類の定型作業で、道具の呼び出しは 61 回（すべて 1 応答に 1 個）でした。

## 試算: 何を減らすと効くか

| 対策 | 試算 |
|---|---|
| 基礎を 8K 削る（記憶の索引を圧縮・使わないスキルを外す・設定ファイルを薄くする、を全部） | **−2.7%** |
| 応答数を 23% 減らす（62→48） | **−20%** |
| 応答数を 38% 減らす（62→38） | **−32%** |

![基礎を 8K 削ると −2.7%、応答数を 23% 減らすと −20%、38% 減らすと −32%。無くせた往復の型は、同じ長い文字列を 2 回書いた・出力の切り詰め幅を 3 回試した・無い道具を 4 手探した・同じ器を 2 連で走らせた](/images/where-tokens-go-claude-code/n1_lever.png)

基礎 8K は「できる限り削った量」です。それでも 2.7%。応答を減らすと**基礎の再計上と積み上げの再計上の両方**が減るので、1 桁効きます。

**重みを振っても順位は変わるか（感度・09-16 に 1 回）**: 同じ転写で重みを 7 通り（本文の 0.1／2／5／1、料金比に近い 0.1／1.25／5／1、cache_read 0.05 と 0.2、output 3 と 10、等重み 1／1／1／1）に振ると、基礎 8K の削減は **−1.9〜−4.6%**、応答 23% 減は **−18〜−23%**、38% 減は **−30〜−38%**。内訳の比率（基礎 28〜52%・出力 1〜34%）は重みでかなり動くので、35／20／45 という数字自体に意味を持たせないでください。動かないのは「削る量より払う回数」の順位だけです。

23% は、依頼①の転写を見直して「無くせた往復」を数えた値です。型は 4 つ——同じ長い文字列を 2 回書いた（書き込みに失敗して書き直し）、出力の切り詰め幅を 3 回試した、無い道具を 4 手探した、同じ器を 2 連で走らせた。どれも作業の量ではなく、往復の作法の問題でした。

## 自分の Claude Code が重いときの確認順

1. **単位を確かめる**——応答数を `message.id` で数える（行で数えない）
2. 基礎相当量（1 応答目の cache_creation＋cache_read）を見る
3. 出力の合計を見る
4. 積み上がった会話（cache_read − 基礎×(N−1)、cache_creation の増分）を見る
5. **「削る量 × 毎回払う回数」で優先順位を決める**——基礎を X 削れば X×0.1×(N−1)、応答を 1 回減らせば（基礎＋積み上げ）×0.1

## 誤解しやすい点

- **行数≠応答数**。私は最初に行で数え、出力の重みも二重に足して「出力が 39%」と出した。id で数え直すと 62 応答・出力 20%。
- **35／20／45 はトークン数の比率ではない**。重み付きスコアの比率。生のトークンでは 97% がキャッシュ読み。
- **キャッシュ読みは、この比較モデルではゼロ扱いしない**。0.1 倍でも応答数ぶん積む。
- **会話を分けても基礎は減らない**。新しい会話でも毎応答同じ基礎が再計上される。減るのは積み上がった分だけ。
- **積み上げ 45% は「情報収集が無駄」ではない**。作業の量そのもの。無駄だったのは往復の数のほう。
- 長いセッションほど積み上げの再計上が支配的になる（同じセッション全体 232 応答の時点で 71%）。往復の効きは増す。

## 往復を減らすには

独立な道具の呼び出しを同じ応答に並べる、失敗の撃ち直しをなくす、無い道具を探し回らない。その行動をどう変え、変わったことをどう測ったかは次の記事に書きます。ここでは「往復数が効いた」という観測までにします。
