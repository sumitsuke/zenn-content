落ちないのに数字が合わないとき、どこを直せば消えるのか。自分のアプリ（Rust／Tauri・クローズドβ・ソロ開発）で「データの整合性に問題 8 件」というバナーが消えず、4 本の PR で 4 つの層を順に直して、ようやく消えました。その記録を、層別に追う手順として書きます。

## 先に結論

- 数字は **計算 → 保存 → 読み出し → 表示** の 4 層を通って画面に出る。自分が踏んだ 6 件のうち、表示だけが原因だったのは 2 件。残りは保存・読み出し、そして「書く経路が無い」だった。
- 同じバナーに対して 3 回外した。保存（SET 句に列が無い）、保存（別トランザクションの窓）、読み出し（古いコピーを読む）——どれも「計算は正しい」まま。
- 表示が最初にズレた層なら、表示を直す（下の 2 件がそれ）。下の層がズレているのに表示で辻褄を合わせると、別の画面が狂う。**最初にズレた層を見つけて、そこを直す。** それだけです。

## 先に除外する 5 つ

「数字が合わない」の多くは、まずこの 5 つのどれかです。端・境界・再実行で試すと出ます。

1. **端数処理の不統一**——floor と round が場所で混在。丸めは一箇所に固定する
2. **浮動小数**——`0.1 + 0.2` は `0.3` にならない。金額は最小単位の整数で持つ
3. **集計の境界**——月またぎ・締め時刻・タイムゾーン
4. **off-by-one**——`<` と `<=` の取り違え。閾値ちょうどの値で試す
5. **二重加算**——再送・リトライ・連打。冪等（同じ処理を 2 回やっても結果が変わらない性質）にする

この 5 つに当たらないとき、層で追います。

## 表示層で起きていた 2 件

**逆転表示（PR #384）**: 履歴画面の「上位%」列が、遅いセッション（p91）を速いセッション（p9）と同じ「上位 9%」と表示していました。裏側の定義は「値が大きいほど遅い」。表示側だけが `percentile < 50 ? p : 100 - p` と折り返していた。監査で見つけた計算の修正 6 件のうち、これだけが P1 でした。直しは、折り返しをやめて生のパーセンタイルを出し、速い／遅いは色で示すこと。

**経路で違う統計量（PR #456）**: 結果画面の見出しだけが平均（195）で、推移・ダッシュボード・集団比較は中央値（206）。見出しだけが孤立して、画面間で数字が一致しない。中央値に統一しました。

どちらも「計算は正しく、保存も正しく、表示が違う」型で、ここまでは表示層で完結します。問題は次からです。

## 消えないバナーを、4 本の PR で（保存 2・読み出し 1・観測 1）

![計算→保存→読み出し→表示の 4 層と、各層で外した PR の対応図。外した 3 回は保存 ×2・読み出し ×1](/images/numbers-dont-match-4-layers/four-layers.png)

症状は 1 つで、「データの整合性に問題 8 件」というバナーが、直しても再ビルドしても消えない。

### 1 本目・保存（PR #455）: 計算した値が SET 句に無かった

完了処理は整合性ハッシュ（データが後から書き換えられていないか照合するための短い値）を計算して、構造体に積んでいました。ところが完了時の `UPDATE` の SET 句にその列が無く、**計算値は捨てられていた**。実 DB を見ると、完了行のうちハッシュを持つ行は 0。検証の仕組みは実質、動いていませんでした。

設計者も監査者もハッシュの「計算」は確かめていたが、「永続化（SET 句）」は誰も確かめていなかった。直しは 2 つです。

- 列を SET 句に足す
- 既存行に、現在の列値からハッシュを埋める migration を入れる

### 2 本目・保存（PR #458）: 書き換えと再ハッシュが別トランザクション

1 本目で永続化されると、今度は別の窓が見えました。ハッシュ対象の列を正当に書き換える処理と、その再ハッシュが別トランザクション。書き換えのあと・再ハッシュの前にダッシュボードが読むと、「新しい値＋古いハッシュ」で全件が改ざん扱いになる——それが 8 件でした。ログでは `stored=a72c30c0` に対して `computed=fceca289`（`computed` は現在の列値から計算した値）。再ハッシュが終わると一致するので、**窓の間だけの一時的な不一致**です。

直しは、書き換えと再ハッシュを 1 トランザクションにまとめることです。

### 3 本目・読み出し（PR #459）: 列を直しても、読む側は別の場所を見ていた

それでも消えず、今度は読み出し層でした。ハッシュは平文の列で維持されているのに、暗号化されたペイロードの中にも、暗号化時点で固定されたコピーがあり、復号経路の read はそちらを読んでいた。1 本目も 2 本目も「列」を直していたのに、**read が列を見ていなかった**ので効いていなかった。

直しは read を平文列に向けることで、ここでバナーは消えました。

### 4 本目・観測（PR #517）: 見逃す条件を潰す

最後に、改ざん検知が特定の条件では黙って見逃していたので、検知時は常に警告を出し、対象セッションを識別できるようにしました。数字の問題が直っても、次に起きたとき気づける状態にしておかないと、また 3 回外します。

## 手順として書き直す

1. **再現を固定する**——どの操作で・どの値が・どうズレるかを、毎回同じ手順で出せるようにする
2. **層別に追う**——計算 → 保存 → 読み出し → 表示 の順に、各層の値をログで出して並べる。上の例なら「計算した hash／DB の列の hash／read が返した hash／画面の件数」の 4 つ
3. **最初にズレた層を犯人にする**——表示だけで辻褄を合わせない（表示が最初にズレた層なら、表示を直す）
4. **窓を消す設計にする**——関連する書き換えは 1 トランザクションに。read は書いた場所を読む（コピーを読まない）
5. **再発防止テストを 1 本残す**——「完了処理のあと DB に hash が入っている」のような end-to-end の 1 本。上の 1 本目は、このテストが無かったから見逃した

対症療法は新しいバグの種です。少し手間でも、層をたどって根を断つほうが、結局速い。

## 層の前に確かめること: 書く経路がそもそも在るか（PR #369）

「基準値に含まれません」が全セッションに出ました。読む関数はあるのに、書く関数はセッション削除時からしか呼ばれておらず、通常運用では基準値が永久に作られない。実測は、完了 27 件・基準値 0 行・スコア全 None。計算も保存も表示も正しく、**書く経路が無い**。これは 4 層のどこかがズレたのではなく、層に入る前の前提（値を作る経路が存在するか）が欠けていた例です。層で追う前に、まずここを確かめます。
