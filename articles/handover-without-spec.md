「仕様書はありますか」と聞く前に、無いものとして読み始める。ココナラの公開募集 881 件を語で分類したら、修理・改修・引き継ぎ系 256 件のうち、本文に仕様書・設計書・ドキュメント系の語が出てくる依頼は 26 件（10%）でした。この記事は、その数字と、仕様書がない前提で相手のコードを読むときに私がやっている手順を書きます。手順の 2 つは、受託で実際に踏んだ穴から来ています（時期・相手・技術は書きません）。

## 先に結論

- 引き継ぎ・修理の依頼は、9 割が**本文に仕様書・設計書・ドキュメント系の語を含まない**。「仕様書は無い」を既定として読む手順が要る。
- 正は仕様書ではなく 2 つある。**現状の正**＝動いている現物（コード・画面・データ・ログ）と、**要求の正**＝依頼文の逐語・合意した条件。仕事は「現状の正を要求の正へ変える範囲」を特定すること。原文は必ず残す——要約は索引で、判断は原文へ戻る。
- 着手前に 1 行だけ聞く——「この版で凍結ですか。作業中に変更が入りますか」。聞かなかったときは、納品の直後に作り直しになりました。

## 実数: 881 件の募集を語で分けた

対象は、ココナラの公開募集を私の台帳に取り込んだ 881 件（重複除外・取得 2026-06-24〜2026-09-15）です。分類は募集文の語による機械的な当てはめ（意味の判定ではない）なので、粗い数字として読んでください。依頼主・案件の中身は出しません。語の条件は末尾の注に置きます。

| 分類 | 件数 | 割合 |
|---|---|---|
| 修理・改修・引き継ぎ系（修正／改修／バグ／エラー／不具合／動かない／引き継ぎ／既存／復旧 の語） | 256 | 29%（881 件中） |
| うち、仕様書・設計書・ドキュメント系の語が本文にある | 26 | 10%（256 件中） |
| うち、「仕様書があります／用意してある」と明記 | 3 | 1% |
| うち、上の語が本文に無い | 230 | 90% |
| うち、AI・ノーコード系の語が本文にある（「AI 不可」の類 2 件を含む） | 56 | 22% |

「用意してある」と明記した依頼は 256 件中 3 件。語が無い 230 件のうち、実際には仕様書がある依頼も混ざっているはずですが、こちらからは見えません。26 件のほうも「仕様書を作ってほしい」「ドキュメント整備も」のような依頼を含むので、「有無に触れた」件数ではなく「語が出た」件数です。受ける側の現実は「無いものとして読み、あったら儲けもの」です。5 件に 1 件は本文に AI・ノーコード系の語があり（作った・使ってよい・使うな、を区別しない語の当てはめ）、AI に作らせたものは作った本人にも構造が説明できないことがある。

## 「仕様書がない」の正体は 3 つ

読み始める前に、無いものの種類を分けておくと手が決まります。

1. **本当に無い**——作った人が去った、AI に作らせた、動いたので書かなかった
2. **依頼主の頭の中にある**——「あの画面をこうしたい」が仕様の全部。文字にはなっていない
3. **コードが仕様**——動いている挙動そのものが正で、それ以外の定義が無い

3 つとも、こちらの手は同じです。**仕様書を復元せず、2 つの正を立てる。**

- **現状の正（As-Is）**＝実際に動いているコード・画面・データ・ログ。「いまどう動いているか」を示す
- **要求の正（To-Be）**＝依頼文の逐語と、合意した条件。「依頼主が何を変えたいか」を示す

現物が「ボタンを押すと A になる」、依頼文が「B になるよう直してほしい」なら、どちらも正で、意味が違う。現物を理想の仕様だと思い込む事故と、依頼文を現在の挙動だと思い込む事故を、分けておくことで両方防げます。作業者の仕事は、**現状の正を要求の正へ変える範囲だけを特定する**こと。仕様書を先に書き起こすのは、直す前に別の納品物を 1 つ増やすことで、依頼主が求めていない仕事です。下の 5 手順は、この 2 つの正を固定して、その間だけを動かす手順です。

## 手順 1: 依頼文の逐語を保存してから読む（要求の正を固定する）

依頼文・画面キャプチャ・ログを、受け取った形のまま保存して、引用はそこから写します。要約は索引として使ってよい。ただし**要約を正本にしない**——判断の根拠は原文へ戻る。「基本系」と丸めた要約を見て実装し、括弧の中に書かれていた条件を落としたことがあります。

もう 1 つの理由は、契約前は質問が返ってこない前提で進めるので、**手元の逐語がそのまま要求の正**になること。原文は保存する。ただしログや画面には API キー・メールアドレス・顧客データ・ファイルパスが混ざるので、外部に出す資料へ転記するときはマスクする。

不明点は相手への質問に変換せず、前提を宣言して「できること／できないこと」の形で書く。返信が来なければその前提で進む、と添えます。

## 手順 2: 入口から現物を追う（現状の正を観測する）

読む順番は、起動 → 画面 → データ → コードです。コードから入ると、動いていない部分まで読んでしまう。

- **起動**: 何を実行すると動くのか（コマンド・URL・ファイル）。動かなければ、そこが最初の修理箇所
- **画面**: 依頼文に出てくる画面を、実際に開く。依頼文の語と画面の語が一致しない箇所を控える
- **データ**: 入力と出力の実物を 1 組取る。DB なら該当テーブルの行数と 1 行のサンプル
- **コード**: 画面とデータをつなぐ経路だけ読む。全体は読まない

「依存する相手側の機構は、本体を読んだか」を自分に問います。呼び出し側だけ読んで「こう動くはず」と書くと、そこが外れます。

## 手順 3: 着手前に 1 行聞く——「この版で凍結ですか」（現状の正を動かさない）

相手のコードに手を入れる依頼では、着手のあとに相手側でコードが変わることがあります。納品物が「このファイルの何行目」を指していれば、その時点で行番号がずれて、作り直しになる。私はこれを一度やっています——受け取ったソースに対して作った納品物を、相手側の変更のあとで丸ごと作り直しました。動いている的を撃っていました。

言わなかったのは相手、聞かなかったのはこちら。聞くのは 1 行です。

> この版で凍結ですか。作業中に変更が入りますか。

入る場合は、照合 ID（ファイルのハッシュ）を先に決めておきます。それでも凍結されるとは限りません（聞いても、納品のあとに相手側で変更が入ることはあります）。だから次の手順が要ります。

## 手順 4: 行番号を目印にし、逐語を正にする（対象箇所を再識別できるようにする）

納品物で「`main.js` の 120 行目を直してください」と書くと、相手の編集で 1 行ずれた瞬間に嘘になります。私は、**行番号は目印、逐語を正**にしています。

```
場所: main.js（目印: 120 行目付近）
逐語: `if (count = 0) {`          ← この行を探す
直し: `if (count === 0) {`
```

相手が探す手がかりは「120 行目」ではなく「この文字列」。行がずれても、逐語で検索すれば到達します。

## 手順 5: 未検証の面を、そのまま報告に写す（観測できなかった境界を明示する）

仕様書がない引き継ぎでは、確かめられなかった面が必ず残ります。それを報告から落とさない。

- 読んだが動かしていない経路
- 依頼主の環境でしか再現しない可能性がある挙動
- 前提を置いて進めた箇所（「〜と仮定して直しました」）

「確認できなかった」と書くほうが、「対応済み」と書いて後で崩れるより、次の依頼につながります。

## 手順として 1 枚に

1. 依頼文・画面・ログを逐語で保存する → **要求の正**を固定（要約は索引。判断は原文へ）
2. 起動 → 画面 → データ → コード の順に現物を追う → **現状の正**を観測（経路だけ読む）
3. 着手前に「この版で凍結ですか」を 1 行聞く → 現状の正を動かさない（入るなら照合 ID）
4. 納品物は行番号でなく逐語をアンカーにする → 対象箇所を再識別できるようにする
5. 未検証の面を報告に写す → 観測できなかった境界を明示する

仕様書を復元するのは、この 5 つの後で、依頼主が求めたときだけです。

手順 5 の「未検証を残す」を含めて、受け取ったものの判定を 1 枚に残す型は [AI 生成コードの検収シート](https://sumitsuke.jp/via/zenn/lab/ai-code-acceptance-sheet/)（Markdown 1 枚・CC0）にしています。

### AI の利用について

881 件の分類は、語による機械的な当てはめ（Python スクリプト・再実行で同じ数字が出ます）で、AI による分類ではありません。この記事は AI（Claude）が下書きし、数字の照合・実話の一般化の粒度・公開の判断は人間が行いました。依頼主と案件の中身は出していません。

### 注: 分類の語（意味判定ではない）

- 対象＝募集の題名・見出し欄（依頼工程・用意してあるもの等）・本文。募集者名の行と私の台帳注記は切り落とす
- 修理・改修・引き継ぎ系＝`修正／改修／バグ／エラー／直し／不具合／動かな／引き継／既存／復旧／復元`
- 仕様書系＝`仕様書／設計書／要件定義／ドキュメント／マニュアル／README／設計資料`
- 「用意してある」＝`仕様書（が）あります／をお渡し／を用意` などの言い回し
- AI・ノーコード系＝`AI（英単語の一部と Illustrator の (AI) は除く）／ＡＩ／ChatGPT／Claude／Copilot／Gemini／Cursor／ノーコード／バイブ／vibe`。「AI 不可」の依頼も数に入る
- 同じ依頼が複数の分類に入ることはある（修理系の中で仕様書系と AI 系は重なりうる）

### 受託でも同じ手順で読んでいます

「作った人がいない」「仕様書がない」「AI に作らせたが直せない」——そういう相談を、テキストだけで受けています。着手前に「できること／できないこと」を文書で渡します。
