生成 AI に書かせたコードは、どこで壊れるのか。症状の一覧ではなく、自分のリポジトリ（Rust／Tauri のデスクトップアプリ・クローズドβ・ソロ開発）で実際に踏んで直した 3 件を、PR と commit の番号つきで書きます。ローカル LLM に書かせた 120 本を測った結果も添えます。

## 先に結論

- 自分のリポで踏んだ壊れ方は、大きく 3 つだった——**失敗を隠す／無いものを本当らしく書く／検証が緑のまま通る**。
- 3 つとも、コードを読むだけでは見つからなかった。見つかったのは、「通った」という証拠を**別の角度からもう一度取った**とき。
- 生成 AI は「通る形」を作るのが上手い。確かめる側は、通ったかどうかではなく、**通らない条件を作って落ちるか**を見る（この記事では「毒テスト」と呼びます。毒テスト＝わざと失敗条件を入れて、検査器が本当に赤になるかを確かめるテスト）。

![3 つの型と見つけ方の一覧。型 1 失敗を既定値で埋めて通す・型 2 存在しない出典を本物の形で書く・型 3 終了コードが固定されて緑のまま通る](/images/ai-code-breaks-3-patterns/three-patterns.png)

## 型 1: 失敗を、広い権限や既定値で埋めて通す

```python
try:
    rate = fetch_tax_rate()
except Exception:
    return 0   # 取得失敗を「税率 0%」として続行。画面は正常、金額だけが誤り
```

例外を飲み込んで既定値を返す。取得に失敗したら「とりあえず通る値」で続ける。エラーは出ず、テストも緑で、結果だけが違う——これが型 1 です。

**実例（PR #524・2026 年 6 月）**: Windows で鍵ファイルの ACL（誰がアクセスできるかの一覧）を絞る関数が、環境変数 `USERNAME` の取得に失敗すると `BUILTIN\Users`（全ローカルユーザー）に Full Control を付与して続行していました。失敗を「広い権限」で埋めるので、例外は出ない。テストも通る。鍵ファイルだけが開いている。

直しは「失敗したら閉じる」方向です。SYSTEM と Administrators だけを残して警告ログを出し、`icacls` の引数の組み立てを純粋関数に分けて、この分岐の回帰テストを 2 件足しました。

**見つけ方**: 「握り潰すコードを検出器で数えれば混入率が出る」と考えて、ローカル LLM に書かせた Python と TypeScript 120 本を Semgrep と AST で測ったことがあります（[Qiita の実測記事](https://qiita.com/sumitsuke/items/dc2a839a8f3618d0da12)）。検出器が挙げた候補は 4 件、人手で開くと**真陽性は 0 件**でした。同じ `return None` でも、数値の変換なら正当で、HTTP の取得なら 404 も断線も潰す欠陥——構文では判定できません。

自分の検証で効いた読み方は 1 つでした。関数ごとに「失敗したら何が起きるか」を、**呼び出し側の期待と突き合わせて**読む。検出器は候補を出すところまで、判定は人がやる。

**直し方**: 失敗時の既定を「閉じる・止める・記録する」にする。既定値で続けてよいのは、その関数の契約（docstring）に書ける場合だけです。

## 型 2: 存在しない出典・数値・参照を、本物の形で書く

もっともらしい出典、もっともらしい数値、存在しない関数や設定キー。読んだだけでは本物と区別がつかず、実行しても露見しません。「コードが動く・テストが緑」とは独立した問題です。

**実例（PR #546・2026 年 6 月）**: 製品の中に「309 ms／SD 106／N=80（Matzke & Wagenmakers 2009）」という帰属つきの数値がありました。監査で疑い、原典の全文 90,664 字を検索して——**その数値は原典にありませんでした**。同じ PR で、存在しない「§Method of Moments」という参照も見つかっています。

直しは 3 つ。

- 架空のコホート表示（N=80・年齢 24.3±3.8）と、対応する i18n の 5 キー×2 言語を除去する
- 帰属ラベルを実在の文献（Woods et al. 2015・N=1,469）に置き換える
- 計算は元から自前のシミュレーション由来と明記してあったので、数値と挙動は変えない

**見つけ方**: 固有名詞・数値・出典は、AI の要約ではなく**原典で全文検索**する。帰属の形式（著者・年・N・SD）が整っているほど読む側は通すので、「それらしい」ほど疑う。パッケージ名や API 名も同じ型ですが、自分で踏んだ実例が無いので、ここでは触れるだけにします。

**直し方**: 出典に到達できない数値は出さない。到達できたら、到達した場所（URL・ページ・検索した文字列）を残す。

## 型 3: 終了コードが固定されていて、検証が緑のまま通る

テストも CI も緑。壊れているのは測定器のほう、という型です。

**実例（commit 4b670a2a・2026 年 6 月）**: バッチ実行スクリプトの 3 経路が、終了コード（プロセスが成功か失敗かを返す数）を 0 に固定していました。テストの失敗数が、プロセスの外に伝わらない。同じ commit で逆方向も直しています——スキーマ検査ツールが古いコメント行に fallback（本命が外れたときの代替）でマッチして、**偽の FAIL** を出していた。緑も赤も根拠が壊れていたので、直したあとは毒テストで確かめました。わざと偽のテーブルを注入して、FAIL と exit 1 になるかを見る。

もう 1 件。同じ時期の PR 本文に、こう書き残しています。「直前の commit メッセージの『ci-local full PASS』は、作業ディレクトリの残留で未実行のまま記載していた誤り」。**緑だと書いた本人が、実行していなかった。** 型 3 は道具だけでなく、書く側にも起きます。

**見つけ方**: 緑を信じる前に、毒を 1 本入れて赤になるかを見る。0 件で緑になる検査は検査ではない。緑の主張には、実行ログ（いつ・何件・どこに出たか）を添える。

**直し方**: 終了コードは失敗数から作る。検査対象が 0 件なら赤にする。「PASS」と書くときは、ログの場所を同じ行に書く。緑が嘘になる型は 4 つあるので、別記事にまとめます。

## 3 つに共通すること

3 型とも、コードの見た目は「正しく動く形」をしていました。生成 AI は形を作るのが上手く、形が整っているほど人は読み飛ばす。だから確かめる側の仕事は、次の 3 つに絞れます。

1. **失敗経路を先に列挙する**——「失敗したら何が起きるか」を関数ごとに、呼び出し側の期待と突き合わせて読む
2. **出典・数値・名前は原典で全文検索する**——到達した場所を残す
3. **緑の検査には毒を入れる**——赤になるのを見てから信じる

コードとテストを同じ AI に書かせると、同じ思い込みを共有して両方緑になる型（相関誤差）は、別記事「[AI 生成コードがテスト緑でもすり抜ける理由](https://zenn.dev/tauridev/articles/4bb102996181fe)」に書きました。
