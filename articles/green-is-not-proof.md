自動検査の「緑」は、どういうときに当てにならないか。私は数か月、自作の検査器を運用して、捕まえた欠陥より直した回数のほうが多くなり、廃止しました。そこまでに踏んだ「緑の嘘」を 4 つの型に分け、再現手順と一緒に書きます。

## 先に結論

- 自作の検査器は、**捕まえた欠陥 5 件に対して、検査器自体を直した回数が 22 件**。数えた時点で廃止し、残したのは「要件を満たしているか」「本当に動くか」の 2 本だけ。
- 緑が嘘になる型は 4 つ——①終了コードが固定・伝わらない ②対象が 0 件で緑 ③器が別の物を見ている ④器が原理的に見えない領域。
- 見つけ方はどれも同じ。毒を 1 本入れて赤になるのを見る（毒テスト＝わざと失敗条件を入れて、検査器が本当に赤になるかを確かめるテスト）。読むのは終了コードではなく、**「何件を見た」という出力の中身**。

![「緑」が出る 5 つの経路。本物は「検査が走って赤にならなかった」の 1 つだけで、残り 4 つ（終了コードが固定・対象 0 件・別の物を見ている・原理的に見えない領域）は同じ緑に見える](/images/green-is-not-proof/green-routes.png)

## 型 ①: 終了コードが固定されている・伝わらない

`exit 0` が保証するのは「プロセスが異常終了しなかった」ことだけで、「検証が行われたか」とは無関係です。ところがその exit 0 すら、素直に信じられない場面がある。

**再現（Node v24.14.0・2026 年 9 月）**: `node --check` は、**`import` か `export` を含む `.js`**（ESM 構文の `.js`）の構文エラーを、exit 0・エラー出力なしで素通りします。同じ中身を `.mjs` にすると捕まえる。⚠ 素の CJS の `.js` は正しく exit 1 になるので、条件を落とすと再現しません（09-16 に条件を確定）。

```bash
printf 'import fs from "node:fs";
function ((){
' > 毒.js   # import を含む .js に構文エラー
node --check 毒.js  ; echo $?   # → 0（素通り・stderr なし）
cp 毒.js 毒.mjs
node --check 毒.mjs ; echo $?   # → 1（捕まえる）
```

この素通りのまま「構文チェックは通っています」と書いた報告が 1 通、私の手元から出ています。毒を入れて初めて分かりました。

もう 1 つ。`cmd | head -20` の終了コードは `head` のものです。赤い検査をパイプで切ると緑に見える。終了コードを読むならパイプの手前で読む（`set -o pipefail` にするか、ファイルに落としてから切る）。

## 型 ②: 対象が 0 件で緑になる

営業文の点検器を作っていました。貼り付け用テキストの形式を変えた日、点検器は「貼る範囲が決まらない」と言って、**1 件も検査せずに終わりました**。ラッパーの `EXIT=0` だけを見ていた私には緑に見え、以降の数便がすべて素通りしていた。

当て直したら、その場で実害が 2 件出ました。「62 項目」と書いていた文書の生成物は 61 項目。同じ便の「〜のときだけ効く仕様はそのままです」という文は、その日の作り直しで偽になっていた。送信前だったので直せました。

**直し方**: 合否を終了コードでなく**実行件数**で出す。最小のゲートはこれだけです。

```bash
passed=$(grep -oE '[0-9]+ passed' result.log | grep -oE '[0-9]+')
failed=$(grep -oE '[0-9]+ failed' result.log | grep -oE '[0-9]+')
ran=$(( ${passed:-0} + ${failed:-0} ))

if [ "$ran" -eq 0 ]; then
  echo "UNVERIFIED: 0 件実行（緑でも検証されていない）"; exit 1
elif [ "${failed:-0}" -gt 0 ]; then
  echo "FAIL: ${failed} 件失敗"; exit 1
else
  echo "PASS: ${passed} 件成功（実行 ${ran} 件）"; exit 0
fi
```

形式（ファイル名・置き場所・区切り方）を変えたら、その形の実物を 1 本、検査器に通す。読むのは「何件を見た」と言っているか。**0 件で緑になる検査は、検査ではなく飾り**です。

## 型 ③: 器が別の物を見ている

「欠陥だ」と思った 4 件が、4 件とも道具の側でした。ゲームのサーバーとクライアントで通し試験をしていたときの記録です。

| 見えた症状 | 真犯人 |
|---|---|
| 値が増えた。対象が 2 つあるように見えた | `--tail n` は増え続けるログの末尾を返す。対象が黙ると最後の行を返し続ける |
| 表示が固まって見えた。コマンドが効かない | 「最寄りの 1 体」を取るセレクタが、乗っている対象と別の対象を掴んでいた |
| 別の対象のログが混ざる | 過去の試験用の対象が、近づいた瞬間に起きて動く |
| 再起動で状態が消える | 停止スクリプトが強制終了で、保存の前に殺していた |

うち 1 件は、製品側を書き換えてから道具の側だと気づいて戻しました。**実機で「欠陥だ」と思ったら、報告する前に「その数字はどこから来たか」を 1 回追う。** ログを「いまの状態」として読むなら、行数を覚えて増えた分だけ読む。測る前に、対象の数を数える。

## 型 ④: 器が原理的に見えない領域

同じ案件で、自動の通し実走（27 テスト・1 回約 7 分）を検品として **7 回、計 49 分**回しました。赤は 0 件。同じ日に実機で見つけた欠陥は 5 件以上——描画されない、アイコンが出ない、当たり判定が見た目の 1/12、tick の例外、画面の旧名。

原因は単純で、ヘッドレスの実行環境（画面を持たずに動かす環境）は、見た目・音・当たり判定を読みません。そこは原理的に素通りする。捕捉率 0/7 を数えてから、重い実走は「客先に出す前に 1 回」だけにしました。途中は 1 テストずつ絞って回す。「軽い実走で大体見つかる」かどうかは測っていないので、ここでは書きません。

## 廃止の判断: 22 対 5

![検査器が捕まえた欠陥 5 件に対して、検査器自体を直した回数 22 件の棒グラフ](/images/green-is-not-proof/22-vs-5.png)

上の 4 型を踏みながら、検査器（段・キャッシュ・毒テスト）を育てていました。ある日数えると、**検査器が捕まえた欠陥は 5 件、検査器自体を直した回数は 22 件**。器を信じるための器を作っていた、ということです。

廃止して残したのは 2 本だけです。

1. **要件を満たしているか**——要件の台帳に「根拠」が付いているかを機械で数える。0.1 秒で終わる。
2. **本当に動くか**——実走。ただし客先に出す前に 1 回だけ。途中は 1 テストずつ。

新しい検査を足すときは、先に 3 つ問うことにしました。それは今週の欠陥を捕まえたか。直す回数が捕まえる回数を上回っていないか。人が実物を開くほうが速くないか。

## 共通する 1 行

緑は「検査が走って、赤にならなかった」ときだけ出るのではありません。「検査が走らなかった」「別の物を見た」「見えない領域だった」でも出る。だから信じる前に、**毒を 1 本入れて赤を見る**。

生成 AI が書いたコード側の「緑のまま通る」型は、別記事「[生成 AI が書いたコードが壊れるときの典型 3 パターン](https://zenn.dev/tauridev/articles/ai-code-breaks-3-patterns)」に書きました。検査の結果を「実行／成功／失敗／スキップの件数」で残す型は [AI 生成コードの検収シート](https://sumitsuke.jp/lab/ai-code-acceptance-sheet/)（Markdown 1 枚・CC0）に置いています。
