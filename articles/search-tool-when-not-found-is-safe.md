外付けのドライブを抜いた状態で、手元の書類検索の索引を更新しました。索引が空になり、画面はこう案内しました（同じことを試験で再現すると、3 件あった索引が 0 件になります）。

> まだ索引がありません。フォルダを登録して「索引を作る・更新」を押してください

フォルダは登録してあります。ドライブが見えなくなっただけです。この状態で何かを探すと、答えは「見つかりませんでした」になります。**本当は「調べられなかった」のに。**

この道具は、答えに「検索したファイル N 件」と探した範囲を付ける作りでした。それでも、範囲そのものが消えたり、重なったり、黙って狭まったりすると、付けた範囲はうそになります。外部の精査 2 本が見つけたそういう経路を 14 本の試験にして、「無い」の答えに関わる 10 本を 4 つの型に分けました。

![「見つかりません」がずれる 4 つの型＝①範囲が消えた（R2）②範囲が重なる（R1・R3）③範囲を黙って狭める（R5・R6・R9・R10）④調べられなかった（R4・R8・R12）。14 本中 10 本、ほか 4 本は「無い」に関わらない](/images/search-tool-when-not-found-is-safe/fig1_four_types.png)

**この記事の位置づけ**

- 新しく示すこと: 「探した範囲を答えに付ける」設計でも範囲がずれる経路を 14 本の試験にし、4 つの型と、否定の答えに添える 5 項目にしたこと。
- 当てはまる範囲: 自作の道具 1 つと、作った PC 1 台（Windows 11・Python 3.12.10・SQLite 3.49.1）だけです。試験は 1 回（結果は決まった値が出る）、待ち時間だけ 3 回。探索的な記録として読んでください。

## 4 つの型

### ① 探した範囲が消えた

冒頭の例（R2）です。見えなくなった場所の索引を消してしまうと、次の検索は「無い」と言います。直した後は、前回の索引を残し、「つながっていないフォルダが 1 件あります。前回の索引の中身で探しています（最新ではありません）」と添えて 3 件を返します。

### ② 探した範囲が重なる

- 親のフォルダと、その中のフォルダを両方登録する（R1）→ 同じファイルを 2 回入れようとして、索引づくりが `IntegrityError: UNIQUE constraint failed` で止まりました
- 自分を指すジャンクションを 1 つ置く（R3）→ 同じファイルが 64 件として登録されました

重なると、件数が増えるか、途中で止まって残りを見ないまま終わります。どちらも「見た数」がうそになります。

### ③ 探す範囲を黙って狭める

いちばん数が多い型です（4 本）。

| 試験 | 直す前の答え | 何がずれたか |
|---|---|---|
| R5 35 ファイルに当たる | 「見つかりました（中身で 30 件）」 | 表示の上限 30 を件数として言った |
| R6 1 ファイルに 750 か所 | 600 か所 | 表示の上限の段落だけを数えた |
| R9 あいまい検索で無い | 「段落 1 件の中にありません」 | 候補に絞ったのに、全部を見たように言った |
| R10 「3月決算の資料」 | 中身の結果 0 件 | 「3月」をファイルの日付の条件にして、中身の結果まで絞った |

どれも、道具の中では正しく動いています。**答えの文だけが、実際に見た範囲より広いことを言っていました。**

### ④ 調べられなかった

- BOM の無い UTF-16 のテキスト（R4）→「中身が文字でない」と読み飛ばし、探す語があるのに見つからない
- フォルダを足したのに索引を更新していない（R8）→ 足した場所を見ずに「見つかりませんでした」
- 索引づくりの書き込み中に検索する（R12）→ 直す前は **32.62・32.67・32.68 秒**待ってから `database is locked` の例外。直した版（読むだけの接続）は 3 回とも 0.00 秒で見つかりました

R8 の直した後の答えは「索引済みの範囲には見つかりませんでした（索引を更新していない…）」です。「無い」と「まだ見ていない」を文で分けています。

## 否定の答えに添える 5 項目

画面の文だけでなく、機械が読める形でも返せるようにしました。

```json
{
  "result": "not_found",
  "searched": ["C:/見本/請求書", "C:/見本/見積"],
  "excluded": [{"path": "E:/見本", "reason": "つながっていない（前回の索引で探した）"}],
  "index_updated_at": "2026-09-27T10:02:00+09:00",
  "truncated": false
}
```

![答えの文の前後＝直す前「まだ索引がありません」「見つかりました（中身で 30 件）」「段落 1 件の中にありません」→ 直した後「つながっていないフォルダが 1 件（前回の索引で探した）」「35 件（上位 30 件を表示）」「候補 0 段落を比べた中にありません。段落は全部で 1」](/images/search-tool-when-not-found-is-safe/fig2_answer_before_after.png)

「無い」と言ってよいのは、`searched` が今も在る場所で、`truncated` が false で、調べられなかった場所を `excluded` に名指しできるときだけ。どれかが埋まらなければ、答えは「調べられなかった」です。

社内検索・ログ検索・AI エージェントの「ありません」にも同じ形が当てはまりそうですが、確かめたのはこの道具だけです。

## 試験の回し方

直す前の版で赤が出るかを先に見ました。

```
git archive 6553efb app | tar -x -C <一時フォルダ>
（試験だけ新しい版の run_regress.py を写す）
python <一時フォルダ>/app/tests/run_regress.py   → 合計 0/14
python app/tests/run_regress.py                  → 合計 14/14（直した版）
```

## うまくいかなかったこと

- 書き込み中の待ち時間を、測る前は「待たずに止まる」と記録していました。3 回測ったら約 32.7 秒待っていました。精査に書かれていた 3.04 秒も、この条件では出ていません
- 0/14 → 14/14 は、欠陥から書いた試験なので当然の数です。欠陥の多さの証拠にはなりません
- 14 本は精査 2 本が挙げた経路だけです。4 つの型の外に別の型が無いとは言えません
- この道具を実際に使う側の PC では、この後コードが大きく変わっています。この記事の数は作った PC の時点のものです
